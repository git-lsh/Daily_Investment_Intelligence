# uv (Python 패키지·프로젝트 관리자) 정리

- 카테고리: Foundation
- 도입 시점: 2026-08-27
- 관련 코드 위치: `pyproject.toml`, `uv.lock`, `.python-version`

> 작성 상태: **회고완료**

## 1. 이 기술을 이해하기 위한 사전 지식

uv가 무엇을 해결하는지 이해하려면 아래 개념이 먼저 서 있어야 한다.

- **가상환경(virtual environment)**: 프로젝트마다 독립된 `site-packages`와 인터프리터 심볼릭 링크를
  두어, 프로젝트 A의 pandas 2.x와 프로젝트 B의 pandas 1.x가 충돌하지 않게 하는 장치.
  본질은 "어느 디렉토리에서 패키지를 찾을 것인가"(`sys.path`)를 바꾸는 것이다
- **직접 의존성 vs 전이 의존성(transitive dependency)**: 내가 `yfinance`를 적으면 uv는
  yfinance가 요구하는 `pandas`, `requests` … 까지 함께 가져온다. 내가 적지 않은 이 패키지들이 전이 의존성
- **버전 제약과 의존성 해석(resolution)**: `pandas>=2.0,<3.0` 같은 제약이 패키지마다 붙어 있고,
  모든 제약을 동시에 만족하는 버전 조합을 찾는 것이 의존성 해석. 이것은 일반적으로 NP-hard 문제다
- **다이아몬드 의존성**: A→C, B→C 인데 A와 B가 요구하는 C의 버전 범위가 겹치지 않는 상황.
  Python은 한 환경에 같은 패키지의 두 버전을 둘 수 없어 이때 설치가 실패한다
- **lock 파일**: 해석 결과(정확한 버전 + 파일 해시)를 고정해 둔 파일.
  "언제 어디서 설치해도 같은 환경"을 보장하는 것이 목적
- **sdist와 wheel**: sdist는 소스 배포본이라 설치 시 빌드가 필요하고, wheel은 미리 빌드된 바이너리라
  압축만 풀면 된다. 설치 속도 차이의 대부분이 여기서 나온다
- **`pyproject.toml`**: 프로젝트 메타데이터와 의존성을 선언하는 표준 파일 (PEP 621)

## 2. 기술 개념 정리

**uv는 Rust로 작성된 Python 패키지·프로젝트 관리자**다. 기존에 여러 도구로 나눠 하던 일
— 가상환경 생성(`virtualenv`), 패키지 설치(`pip`), 의존성 잠금(`pip-tools`), 프로젝트 관리(`poetry`),
Python 인터프리터 설치(`pyenv`) — 을 하나의 실행 파일로 통합했다.

두 층위의 인터페이스를 제공한다.

- **pip 호환 층** (`uv pip install ...`): 기존 pip 명령을 거의 그대로 흉내 낸다. 마이그레이션용
- **프로젝트 층** (`uv init` / `uv add` / `uv sync` / `uv run` / `uv lock`): `pyproject.toml`과
  `uv.lock`을 진실의 원천으로 삼아 환경을 선언적으로 관리한다. 이쪽이 본체다

핵심 동작을 말로 풀면 이렇다.

- `uv add <pkg>` 는 `pyproject.toml`의 의존성 목록에 항목을 추가하고, 전체 의존성 그래프를 다시 풀어
  `uv.lock`을 갱신한 뒤, 그 lock 내용대로 가상환경을 맞춘다
- `uv sync` 는 **lock 파일을 기준으로 환경을 정확히 일치시킨다.** 없는 건 설치하고,
  lock에 없는데 설치돼 있는 건 지운다. 즉 환경이 lock 쪽으로 수렴한다
- `uv run <cmd>` 는 실행 직전에 환경이 lock과 맞는지 확인하고, 필요하면 맞춘 뒤 명령을 실행한다.
  덕분에 "가상환경 activate를 깜빡해서 전역에 설치했다"는 실수가 구조적으로 사라진다

속도가 빠른 이유는 언어가 Rust여서만은 아니다. 전역 캐시에 받은 wheel을 풀어 두고, 프로젝트
가상환경에는 **하드링크(또는 copy-on-write)로 연결**해 실제 파일 복사를 피한다. 같은 패키지를
쓰는 프로젝트가 여러 개면 디스크와 시간을 둘 다 아낀다.

`uv.lock`은 `pip freeze` 결과와 성격이 다르다. `pip freeze`는 **지금 이 OS·이 Python 버전에서
설치된 것의 스냅샷**일 뿐이다. 반면 `uv.lock`은 해석 과정에서 나온 **환경 마커(OS, Python 버전,
아키텍처)별 분기까지 담은 크로스플랫폼 lock**이라, Windows에서 만든 lock으로 Linux 컨테이너에서
같은 의존성 집합을 재현할 수 있다. M5에서 Docker 이미지를 만들 때 이 성질이 그대로 쓰인다.

**대안과의 위치 비교**

| 도구 | 가상환경 관리 | 잠금 | 프로젝트 관리 | 비고 |
|---|---|---|---|---|
| pip + requirements.txt | X | 약함 | X | 가장 단순하지만 재현성이 사람 규율에 의존 |
| pip-tools | X | O | X | 잠금은 되지만 환경·프로젝트 관리는 별도 도구 필요 |
| Poetry | O | O | O | 기능은 대응되나 느리고, 과거 표준 미준수 이슈가 있었음 |
| conda | O | 보통 | 보통 | 비-Python 바이너리 의존성(CUDA, MKL 등)에 강함. 무겁다 |
| **uv** | O | O | O | 위 역할을 하나로 통합. 상대적으로 신생 |

## 3. AI/ML 엔지니어 관점에서 알아두면 좋은 개념

ML 배경에서는 "환경이 깨지면 다시 만들면 되지"로 넘어가기 쉬운데, 이 프로젝트에서는
아래 개념들을 짚고 가야 한다.

- **재현성은 모델만의 문제가 아니다.** 시드를 고정하고 데이터를 버전 관리해도, 라이브러리 버전이
  달라지면 결과가 달라진다. lock 파일은 사실상 **"환경의 커밋 해시"** 이고,
  실험 재현성 문제의 절반은 패키징 문제다
- **`pip freeze`가 왜 lock이 아닌가**: (1) 플랫폼·Python 버전에 종속된 스냅샷이라 다른 OS에서 깨지고,
  (2) 어떤 게 내가 원한 패키지고 어떤 게 전이 의존성인지 구분이 없어 정리가 불가능하며,
  (3) 파일 해시가 없어 공급망 무결성 검증이 안 된다
- **의존성 해석은 검색 문제다.** 제약 조건을 만족하는 조합을 찾는 백트래킹 탐색이고,
  그래서 실패할 때 "왜 실패했는지"를 읽는 법(어떤 제약과 어떤 제약이 충돌했는지)이 중요하다
- **공급망 보안(supply chain)**: lock 파일의 해시는 "내가 해석할 때 본 그 파일이 맞는지"를 검증한다.
  이 프로젝트는 외부 금융 API와 LLM API 키를 다루므로, 임의 패키지가 조용히 바뀌어 들어오는 경로를
  막아 두는 것이 의미가 있다
- **개발 의존성 분리**: 테스트·린터는 배포 이미지에 들어갈 필요가 없다. 이 구분을 M0에 해 두면
  M5에서 이미지 크기와 빌드 시간에 바로 이득이 된다
- **이 PC의 특수 사정**: 시스템 `pip`이 Anaconda 배포판에 딸린 것이다. conda 환경과 uv 가상환경을
  섞으면 어느 인터프리터가 쓰이는지 헷갈리기 쉽다. 프로젝트 실행은 항상 `uv run`으로 통일해
  진입점을 하나로 유지한다

## 4. 장점 (이 기술이 잘하는 것)

M0 를 구성하며 실제로 체감한 것들.

- **`uv run` 이 "가상환경을 켜는" 단계를 없앤다.** 이게 생각보다 크다. 이 PC 는 시스템 `python` 이
  Anaconda 배포판이라, activate 를 잊고 명령을 치면 conda 쪽 인터프리터로 실행돼 버린다.
  `uv run pytest` 는 실행 직전에 환경을 lock 과 맞춘 뒤 프로젝트 인터프리터로 돌리므로
  "어느 파이썬으로 돌고 있는지" 를 의심할 일이 없어졌다
- **선언과 상태가 어긋나지 않는다.** `uv add` 로 패키지를 넣으면 `pyproject.toml`(내 의도),
  `uv.lock`(해석 결과), `.venv`(실제 상태) 셋이 항상 같이 움직인다.
  `pip install` 후 `requirements.txt` 갱신을 깜빡하는 부류의 사고가 구조적으로 안 생긴다
- **개발 의존성 분리가 표준 방식으로 된다.** `[dependency-groups] dev` 에 pytest·ruff·mypy 를
  넣어 두면 `uv sync --no-dev` 로 런타임 의존성만 설치할 수 있다.
  M5 에서 Docker 이미지를 만들 때 이 구분이 그대로 쓰인다
- **속도**: 20개 패키지 해석이 1초대, 설치 포함해도 체감상 즉시다.
  느려서 도구 실행을 피하게 되는 일이 없다는 점이 실제로는 가장 큰 이득이다

## 5. 한계점 / 트레이드오프

- **`uv.lock` 은 uv 전용 포맷이다.** 표준(PEP)으로 합의된 lock 파일 형식이 아니라 uv 의 자체 스펙이다.
  나중에 다른 도구로 옮기려면 `uv export` 로 `requirements.txt` 를 뽑아내는 우회가 필요하다.
  즉 **도구에 대한 종속을 감수한 선택**이다
- **비-Python 의존성은 여전히 범위 밖이다.** uv 는 PyPI 생태계 안의 문제만 해결한다.
  이 프로젝트에서 앞으로 필요한 PostgreSQL 서버(M3)나 Docker(M3, M5)는 uv 가 관여하지 않는다.
  conda 가 그 영역까지 다루려 했던 이유를 여기서 이해하게 됐다
- **신생 도구의 문서 공백**: 빌드 백엔드(`uv_build`)로 `src` 레이아웃의 import 패키지명을
  배포명과 다르게(`daily-investment-intelligence` → `dii`) 두려 할 때 바로 되지 않았다.
  `[tool.uv.build-backend] module-name` 을 명시해야 했고, 이건 검색으로 바로 나오지 않는 축에 속한다
- **Python 인터프리터를 uv 가 관리할지 여부가 애매해진다.** 이 PC 에는 Anaconda 파이썬이 이미 있어
  uv 가 그걸 잡아 썼다. 팀 프로젝트였다면 `uv python install` 로 uv 가 받은 인터프리터를 쓰도록
  통일하는 편이 재현성 면에서 나았을 것이다

## 6. 왜 이 프로젝트에서 이 기술을 선택했는가

이 프로젝트의 제약은 (1) 1인 개인 프로젝트, (2) 학습이 목적, (3) 최종적으로 컨테이너·CI 로 간다는 것이다.

- **(3) 때문에 lock 파일이 처음부터 필요했다.** M5 에서 Docker 이미지와 GitHub Actions 로 갈 때,
  "내 PC 에서는 되는데" 를 막아 주는 것이 lock 이다. 그렇다면 `pip + requirements.txt` 는
  시작점으로도 부적절하다 — 나중에 어차피 갈아타야 하고, 이건 D-2 가 말하는
  "겪어 보고 업그레이드할 가치가 있는 재작업" 축에 들지 않는다.
  의존성 관리는 이 프로젝트의 학습 대상이 아니라 학습을 받쳐 주는 바닥이기 때문이다
- **(1) 때문에 도구 수를 줄이는 쪽이 유리했다.** pip-tools + virtualenv + pipx 조합도
  같은 일을 하지만 관리할 도구가 셋이다. uv 는 하나다
- **Poetry 와의 비교**: 기능은 대체로 대응된다. uv 를 고른 실질적 이유는 속도와, `uv run` 이
  가상환경 활성화를 없애 준다는 점이다. 위에 적은 Anaconda 혼용 환경에서 후자가 특히 컸다
- **실서비스·팀 프로젝트였다면?** 결론은 같았을 것이다. 다만 `uv python install` 로 인터프리터까지
  uv 가 관리하게 하고, `uv export` 로 표준 형식 백업을 CI 에 남겨 도구 종속(5절)을 완화했을 것이다
