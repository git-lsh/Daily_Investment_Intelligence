# yfinance (시세 데이터 수집) 정리

- 카테고리: Data Collection
- 도입 시점: 2026-08-27
- 관련 코드 위치: `src/dii/collect/prices.py`, `tests/test_collect.py`

> 작성 상태: **회고완료**

## 1. 이 기술을 이해하기 위한 사전 지식

### 금융 데이터 쪽

- **OHLCV / 일봉(daily bar)**: 하루치 시가(Open)·고가(High)·저가(Low)·종가(Close)·거래량(Volume).
  이 프로젝트의 기본 데이터 단위다
- **거래일 vs 달력일**: 주말과 휴장일에는 데이터가 없다. "3일 전 종가"는 `날짜 - 3` 이 아니라
  **거래일 기준 3칸 전**이다. 이걸 혼동하면 수익률 계산이 조용히 틀어진다
- **수정주가(adjusted price)**: 배당과 액면분할의 효과를 과거 가격에 소급 반영한 값.
  왜 필요한가 — 1주가 2주로 분할되면 종가가 하루 만에 절반이 된다. 미조정 가격으로 수익률을
  계산하면 여기서 **-50% 라는 가짜 폭락**이 잡힌다. 수익률 계산에는 반드시 수정주가를 쓴다
- **생존 편향(survivorship bias)**: 지금 상장되어 있는 종목만 모아 분석하면, 이미 상장폐지된
  실패 사례가 빠져 성과가 과대평가된다. 이 프로젝트는 현재 유니버스를 고정해 쓰므로
  이 편향이 존재한다는 것을 인지하고 시작한다
- **티커 심볼은 안정적인 식별자가 아니다**: 사명 변경, 합병, 클래스 주식 표기 차이
  (`BRK.B` / `BRK-B` / `BRK/B` 가 데이터 소스마다 다르다) 때문에 심볼이 바뀐다.
  장기적으로는 심볼이 아니라 별도 내부 ID 로 종목을 식별해야 한다

### 네트워크 / API 쪽

- **HTTP 상태 코드**: 200(성공), 404(없는 심볼), **429(요청이 너무 많음)**, 5xx(서버 문제).
  429 와 5xx 는 재시도할 가치가 있고 404 는 재시도해도 소용없다 — 이 구분이 수집기 설계의 핵심
- **rate limiting**: 서버가 단위 시간당 요청 수를 제한하는 것. 뚫으려 하는 게 아니라
  **맞춰 주는 것**이 목적이다. 상대 서버 자원을 쓰는 쪽이 우리이기 때문
- **지수 백오프(exponential backoff)**: 재시도 간격을 1초, 2초, 4초… 로 늘리는 전략.
  모두가 같은 간격으로 재시도하면 부하가 몰리므로 무작위 지연(jitter)을 섞는다
- **타임아웃**: 응답이 오지 않을 때 언제 포기할지. 없으면 배치가 무한정 멈춘다
- **타임존과 naive/aware datetime**: 거래소 현지 시각과 UTC 는 다르다.
  타임존 정보가 없는(naive) 날짜와 있는(aware) 날짜를 섞으면 비교 시 예외가 나거나
  하루가 밀린다. 일봉만 다룰 것이므로 **날짜(date)만 저장하고 시각은 버리는** 쪽이 안전하다

## 2. 기술 개념 정리

**yfinance 는 Yahoo Finance 의 비공개 웹 엔드포인트를 감싼 파이썬 래퍼**다.
Yahoo 가 공개한 공식 API 가 아니다. 이 사실 하나가 이 라이브러리의 성격 대부분을 결정한다.

- **계약이 없다.** 공식 API 라면 문서화된 응답 스키마와 SLA 가 있지만, 여기엔 없다.
  Yahoo 가 내부 구현을 바꾸면 예고 없이 깨질 수 있고, 실제로 과거에 여러 번 깨졌다
- **약관상 개인적·비상업적 용도로 제한된다.** 이 프로젝트는 개인 리서치용이므로 범위 안이지만,
  같은 코드를 상업적으로 쓰면 안 된다

주요 인터페이스는 세 가지다.

- `yf.Ticker("AAPL")` — 한 종목의 시세·재무·메타정보 접근. `.history()` 로 시계열을 가져온다
- `yf.download([...])` — **여러 종목을 한 번에** 가져온다. 내부적으로 요청을 묶고 병렬화한다.
  종목이 여러 개면 컬럼이 (필드, 티커) 형태의 MultiIndex 로 나온다
- `yf.Tickers("AAPL MSFT")` — 여러 `Ticker` 객체를 묶은 편의 래퍼

반환 타입은 **pandas DataFrame** 이다. 인덱스가 날짜, 컬럼이 OHLCV. 즉 라이브러리 경계에서
바로 pandas 자료구조가 나오므로, 저장 계층에 넘기기 전에 우리 형식으로 변환하는 지점이 필요하다.

**`auto_adjust` 파라미터**가 이 라이브러리에서 가장 헷갈리는 부분이다.

- `auto_adjust=True` — OHLC 를 전부 수정주가로 덮어써서 돌려준다. 원본 가격은 사라진다
- `auto_adjust=False` — 원본 OHLC 와 별도의 수정 종가를 함께 돌려준다

이 프로젝트는 원본과 수정값을 **둘 다 저장**하는 쪽으로 간다. 이유는 3절에 적는다.
(기본값이 버전에 따라 바뀐 이력이 있으므로, 실제 동작은 구현하며 확인하고 4~5절에 기록한다.)

**대안과의 위치 비교**

| 소스 | 비용 | 성격 | 이 프로젝트 관점 |
|---|---|---|---|
| **yfinance** | 무료 | 비공식 래퍼 | 유니버스 56종목·일봉 수준에는 충분. 안정성 보장 없음 |
| Alpha Vantage | 무료 티어 있음 | 공식 API | 무료 티어의 분당 요청 제한이 빡빡해 56종목 일괄 수집에 불리 |
| Tiingo / EOD HD | 저가 유료 | 공식 API | 계약과 문서가 있음. 안정성이 필요해지면 1순위 대안 |
| Polygon / Databento | 유료 | 공식 API | 분봉·틱 단위까지. 이 프로젝트에는 과하다 |
| Nasdaq Data Link | 혼합 | 공식 API | 데이터셋마다 조건이 달라 파악 비용이 있다 |

## 3. AI/ML 엔지니어 관점에서 알아두면 좋은 개념

### 신뢰할 수 없는 경계를 다루는 법

학습 데이터셋은 보통 한 번 받아서 로컬에 두고 쓴다. 반면 **수집기는 매일 남의 서버에 의존한다.**
정상 동작이 기본값이 아니라는 전제로 짜야 한다.

- **부분 실패가 정상이다.** 56종목 중 3종목이 실패하는 상황이 예외가 아니라 일상이다.
  하나 실패했다고 전체 배치를 중단하면 매일 실패한다. 실패한 것만 기록하고 나머지는 진행해야 한다
- **재시도할 것과 아닌 것을 구분한다.** 429·5xx·타임아웃은 재시도, 404(없는 심볼)는 재시도 무의미
- **타임아웃을 반드시 건다.** 걸지 않으면 응답 없는 요청 하나가 배치 전체를 붙잡는다

### 멱등성(idempotency)

M1 의 완료 조건에 들어 있는 개념이다. **같은 명령을 몇 번 실행해도 결과가 같아야 한다.**

- 수집이 중간에 죽어도 다시 실행하면 이어서 채워야 한다
- 이미 있는 날짜를 다시 받아도 행이 중복되면 안 된다
- 구현 수단은 `(종목, 날짜)` 에 유일 제약을 걸고 INSERT 대신 **UPSERT** 를 쓰는 것이다

이건 ML 파이프라인의 체크포인트/재개와 같은 발상이다. 다만 여기서는 "이어서 학습"이 아니라
"이어서 적재"다.

### 수정주가는 과거가 바뀐다 — 시계열 저장의 함정

이게 이 단계에서 가장 중요한 개념이다.

보통 시계열 데이터는 **한 번 기록되면 불변**이라고 가정한다. 그런데 수정주가는 그렇지 않다.
오늘 배당이 발생하면, **그 이전 모든 날짜의 수정 종가가 소급해서 바뀐다.**

즉 어제 저장해 둔 2020년 1월의 수정 종가와, 오늘 다시 받은 같은 날짜의 값이 다르다.
이걸 모르고 "이미 있는 날짜는 건너뛴다"는 증분 수집을 짜면, 데이터가 조용히 낡는다.

대응은 두 가지다.

1. **원본 OHLCV 와 수정값을 분리해 저장한다.** 원본은 진짜로 불변이므로 증분 수집이 안전하다.
   수정은 파생값으로 보고 필요할 때 다시 계산하거나 갱신한다
2. **최근 구간은 겹쳐서 다시 받는다.** 마지막 적재일부터가 아니라 그보다 며칠 앞에서부터
   다시 받아 덮어쓴다. UPSERT 가 있으니 비용은 요청 몇 개뿐이다

이 프로젝트는 둘 다 쓴다. 저장 스키마 설계(다음 노트)가 이 결정에 직접 묶여 있다.

### 데이터 품질 검증은 수집기의 일부다

받아 온 값이 형식만 맞다고 쓸 수 있는 게 아니다. 최소한 이런 것들을 걸러야 한다.

- 가격이 0 이거나 음수인가
- `low <= open, close <= high` 가 성립하는가
- 같은 날짜가 두 번 들어왔는가
- **미래 날짜**가 들어왔는가 (타임존 처리 실수의 전형적 증상)
- 직전 거래일 대비 변동이 비상식적으로 큰가 (분할 미반영 의심)

ML 로 치면 학습 전 데이터 검증과 같은 자리인데, **여기서 거르지 못한 오류는 파이프라인
맨 끝의 리포트에서 "이상한 종목이 1위"로 나타난다.** 그때는 원인을 찾기 훨씬 어렵다.

## 4. 장점 (이 기술이 잘하는 것)

- **56종목 5년치를 한 번의 호출로 14초에 받는다.** `yf.download()` 에 심볼 리스트를 통째로
  넘기면 내부에서 요청을 묶고 병렬화한다. 종목마다 따로 호출하는 코드를 짜지 않아도 됐고,
  rate limit 도 직접 다룰 일이 없었다. 이 규모에서는 재시도·백오프 로직을 아예 만들지 않았다
- **설치 즉시 쓸 수 있다.** API 키 발급, 인증, 요금제 선택이 없다. 아이디어에서 데이터까지의
  거리가 짧다는 것은 개인 프로젝트에서 생각보다 큰 장점이다
- **pandas DataFrame 으로 바로 나온다.** 응답 파싱 코드를 쓸 필요가 없다
- **`auto_adjust=False` 로 원본과 수정 종가를 함께 준다.** 3절에서 우려했던
  "수정값만 받으면 원본이 사라진다" 문제를 파라미터 하나로 피할 수 있었다.
  실제 응답에 `Open/High/Low/Close/Adj Close/Volume` 6개 필드가 모두 들어온다

## 5. 한계점 / 트레이드오프

- **응답 형태가 심볼 개수에 따라 달라진다.** 심볼이 여럿이면 `(필드, 심볼)` MultiIndex 컬럼이고,
  하나면 평범한 단일 컬럼이다. 같은 함수가 상황에 따라 다른 모양을 돌려주므로
  파싱 코드가 두 경우를 모두 처리해야 했다. 테스트로 양쪽을 고정해 뒀다
- **실패를 예외로 알려주지 않는다.** 존재하지 않는 심볼을 요청해도 예외가 나지 않는다.
  응답에 그 심볼 자리가 NaN 으로 채워져 올 뿐이다. 즉 **호출한 쪽이 직접 판정해야 한다.**
  "실패했으면 예외가 오겠지"라고 가정하고 짰다면 조용히 빈 데이터를 저장했을 것이다
- **라이브러리가 자기 로그를 직접 찍는다.** 심볼 조회 실패를 여러 줄의 ERROR 로 출력하는데,
  우리 수집기가 이미 같은 상황을 판정해 기록하므로 같은 사실이 두 번 찍혔다.
  `yfinance` 로거를 낮춰 중복을 없애고, DEBUG 로 실행하면 다시 보이게 했다
- **비공식 API 라는 근본적 불안정성.** 지금 잘 돌아가는 것과 6개월 뒤에도 돌아가는 것은 다른 문제다.
  이 프로젝트가 감수하는 가장 큰 리스크이고, 대비책은 수집 계층을 얇게 유지해
  다른 소스로 갈아탈 때 이 파일만 바꾸면 되게 해 두는 것뿐이다
- **약관상 개인적·비상업적 용도로 제한된다.** 이 프로젝트의 범위 안이지만, 확장 시에는 제약이 된다

## 6. 왜 이 프로젝트에서 이 기술을 선택했는가

- **규모가 작다.** 56종목·일봉·하루 한 번이다. 유료 API 의 안정성이 필요한 규모가 아니다.
  Alpha Vantage 무료 티어는 분당 요청 제한 때문에 56종목 일괄 수집에 오히려 불리했다
- **D-2(학습 우선, 단계적 업그레이드)에 맞는다.** 무료·비공식 소스로 시작해서
  "비공식 API 는 이렇게 깨진다"를 직접 겪는 것 자체가 이 단계의 학습 내용이다.
  처음부터 유료 API 를 쓰면 5절에 적은 것들을 배울 기회가 없다
- **파이프라인의 본체가 수집이 아니다.** 이 프로젝트의 무게중심은 M3(검색)와 M4(Agent)에 있다.
  수집에서 데이터 소스 선택에 시간을 쓰는 것은 자원 배분이 맞지 않는다
- **실서비스였다면?** 다르게 갔을 것이다. 비공식 API 는 SLA 도 지원도 없어서 장애 시 대응할 수단이 없다.
  Tiingo 나 EOD Historical Data 같은 저가 유료 API 를 쓰고, 소스를 이중화했을 것이다.
  지금 코드가 수집 계층을 얇게 유지하는 이유가 그 전환을 열어 두기 위함이다
