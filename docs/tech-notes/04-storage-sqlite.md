## 1. 이 기술을 이해하기 위한 사전 지식

### 관계형 모델

- **테이블 / 행 / 열**: 데이터를 2차원 표로 표현한다. 행 하나가 사실 하나다
- **기본키(primary key)**: 행을 유일하게 식별하는 열(또는 열의 조합).
  두 개 이상의 열을 묶은 것을 **복합키(composite key)** 라 한다
- **외래키(foreign key)**: 다른 테이블의 키를 참조해 관계를 표현하고 무결성을 강제한다
- **유일 제약(unique constraint)**: 같은 값이 두 번 들어오는 것을 DB 수준에서 막는다.
  애플리케이션 코드가 아니라 **DB 가 막아야** 실수해도 안전하다
- **정규화(normalization)**: 같은 사실을 여러 곳에 중복 저장하지 않도록 테이블을 나누는 것.
  종목 이름을 가격 행마다 반복해 넣지 않고 별도 테이블로 빼는 것이 그 예다

### 인덱스

- **인덱스는 조회를 빠르게 하려고 따로 유지하는 정렬된 자료구조**다. 대부분 B-tree 다
- 없으면 DB 는 테이블 전체를 훑는다(full scan). 있으면 정렬된 구조에서 이진 탐색하듯 찾아간다
- **공짜가 아니다.** 행을 넣거나 고칠 때마다 인덱스도 갱신되므로 쓰기가 느려지고 디스크를 더 쓴다
- **복합 인덱스는 열 순서가 중요하다.** `(symbol, date)` 인덱스는 "특정 종목의 기간 조회"에는
  쓰이지만 "특정 날짜의 전 종목 조회"에는 잘 쓰이지 않는다. 앞쪽 열부터 좁혀 가기 때문이다

### 트랜잭션

- **트랜잭션**은 여러 작업을 하나의 단위로 묶는 것이다. 전부 반영되거나 전부 취소된다
- **ACID**: 원자성(Atomicity), 일관성(Consistency), 격리성(Isolation), 지속성(Durability)
- 이 프로젝트에서 중요한 건 **원자성**이다. 56종목 중 30종목만 적재된 상태로 배치가 죽으면
  다음 실행이 그 어중간한 상태를 이어받아야 한다. 트랜잭션으로 묶으면 그런 상태 자체가 안 생긴다

### SQL

- **DDL** (CREATE TABLE 등, 구조 정의) 과 **DML** (INSERT/UPDATE/SELECT, 데이터 조작) 의 구분
- **UPSERT**: 없으면 INSERT, 있으면 UPDATE. SQLite 와 PostgreSQL 에서는
  `INSERT ... ON CONFLICT (...) DO UPDATE SET ...` 문법을 쓴다.
  M1 의 멱등성 요구가 정확히 이 문법 하나로 해결된다

## 2. 기술 개념 정리

**SQLite 는 서버가 없는 임베디드 관계형 DB** 다. 별도 프로세스로 뜨는 서버가 없고,
애플리케이션 프로세스 안에서 라이브러리로 동작한다. **데이터베이스 전체가 파일 하나**다.

이 구조에서 나오는 성질들:

- **설치·설정·기동이 없다.** 파이썬 표준 라이브러리에 `sqlite3` 모듈이 이미 들어 있다.
  의존성이 늘지 않는다
- **네트워크 계층이 없다.** 연결 문자열, 포트, 인증, 커넥션 풀 같은 개념이 아예 등장하지 않는다.
  뒤집어 말하면 **M3 에서 PostgreSQL 로 갈 때 이 개념들을 그때 처음 배우게 된다**
- **동시성이 파일 락 기반이다.** 여러 프로세스가 동시에 읽을 수는 있지만
  **쓰기는 한 번에 하나**다. 기본 모드에서는 쓰는 동안 읽기도 막힌다.
  WAL(Write-Ahead Logging) 모드로 바꾸면 읽기와 쓰기가 동시에 가능해진다

**주의해야 할 SQLite 고유 성질 두 가지**가 있다.

**(1) 타입이 강제되지 않는다 (type affinity).**
`INTEGER` 로 선언한 열에 문자열을 넣어도 SQLite 는 받아준다. 선언 타입은 "권장 사항"에 가깝다.
다른 DB 를 쓰다 오면 반드시 걸리는 함정이다. 그래서 **`CHECK` 제약으로 직접 막아야** 한다.
(3.37 부터 `STRICT` 테이블 옵션으로 타입을 강제할 수 있다.)

**(2) 날짜/시간 타입이 없다.**
`DATE` 나 `TIMESTAMP` 타입이 없어서 `TEXT`(ISO 8601 문자열), `REAL`(율리우스일), `INTEGER`(유닉스 시각)
중 하나를 골라 규약으로 삼아야 한다. **ISO 8601 문자열(`YYYY-MM-DD`)** 이 사전순 정렬 = 시간순 정렬이
성립해서 비교·범위 조회가 자연스럽고, 눈으로 읽히며, PostgreSQL 의 `DATE` 로 옮기기도 쉽다.

**대안과의 위치 비교**

| 저장 방식 | 부분 수정 | 서버 필요 | 성격 | 이 프로젝트 관점 |
|---|---|---|---|---|
| CSV / Parquet 파일 | 어렵다 | X | 파일 | 수정주가 소급 변경을 반영하려면 파일 전체를 다시 써야 한다 |
| **SQLite** | 쉽다 | X | 행 지향 OLTP | 지금 규모에 정확히 맞고, PostgreSQL 과 SQL 이 거의 같다 |
| DuckDB | 쉽다 | X | 열 지향 OLAP | 분석 쿼리는 더 빠르지만, M3~M4 에서 필요한 건 분석 성능이 아니다 |
| PostgreSQL | 쉽다 | O | 행 지향 OLTP | M3 의 목적지. pgvector 확장이 결정적 이유다 |
| TimescaleDB | 쉽다 | O | 시계열 확장 | 일봉 56종목 규모에는 과하다 |

## 3. AI/ML 엔지니어 관점에서 알아두면 좋은 개념

### 왜 Parquet 이 아니라 DB 인가

데이터 분석 배경에서는 "그냥 parquet 으로 떨구면 되지"가 자연스러운 반응이다.
이 프로젝트에서 그게 안 되는 이유는 앞 노트에서 정리한 **수정주가 소급 변경** 때문이다.

Parquet 은 새 파일을 덧붙이기(append)는 쉽지만 **이미 쓴 파일의 특정 행을 고치기는 어렵다.**
배당이 발생해 과거 5년치 수정 종가가 전부 바뀌면 파일을 통째로 다시 써야 한다.
DB 는 `UPDATE` 한 줄이다. **"부분 수정이 필요한가"가 파일과 DB 를 가르는 실질적 기준**이다.

### long(좁은) 형식으로 저장하고, 분석할 때 wide 로 편다

pandas 로 분석할 때는 행이 날짜, 열이 종목인 **wide** 형태가 편하다.
하지만 저장은 **long**(한 행 = 한 종목의 하루) 으로 한다.

- 종목을 추가해도 스키마가 바뀌지 않는다. wide 로 저장하면 종목 추가가 곧 `ALTER TABLE` 이다
- 종목마다 상장일이 달라 생기는 빈칸을 저장할 필요가 없다 (CEG 는 2022년부터다)
- 제약과 인덱스를 걸 수 있다

즉 **저장 형식과 분석 형식은 다르며, 그 변환은 조회 계층의 책임**이다.

### 인덱스는 조회 패턴에 대한 투자다

이 프로젝트에는 두 가지 조회 패턴이 있고, 그게 인덱스 설계를 결정한다.

- **"AAPL 의 최근 6개월"** — 종목으로 좁힌 뒤 기간. 복합키 `(symbol, trade_date)` 가 그대로 쓰인다
- **"2026-08-26 의 전 종목"** — M2 의 횡단면 랭킹이 이 패턴이다.
  앞의 복합키로는 효율이 안 나오므로 **`trade_date` 단독 인덱스를 따로 둔다**

두 번째 인덱스는 지금 당장 필요하지 않다. 그런데도 두는 이유는 M2 가 확정된 계획이고,
비용(쓰기 지연·디스크)이 이 규모에서 무시할 수준이기 때문이다. 근거 없이 미리 만드는 것과는 다르다.

### 대량 삽입은 트랜잭션으로 묶는다

행을 하나 넣을 때마다 커밋하면, 매번 디스크에 강제로 기록(fsync)하느라 극도로 느려진다.
수천 행을 한 트랜잭션에 묶으면 수십~수백 배 차이가 난다.
**"느린 건 SQL 이 아니라 커밋 횟수"** 라는 감각을 여기서 얻어 둘 만하다.

### 제약은 방어선이지 유효성 검사의 대체재가 아니다

`CHECK (close > 0)` 같은 제약은 **버그가 있어도 잘못된 데이터가 저장되지 않게** 막는다.
하지만 제약 위반은 예외로 터지므로, 수집기는 그 전에 자체 검증을 해서
**"이 종목은 이런 이유로 건너뛴다"** 를 로그로 남길 수 있어야 한다.
DB 제약은 마지막 방어선이고, 첫 방어선은 수집기다.

### 스키마도 버전이 필요하다

테이블 구조는 반드시 바뀐다. SQLite 에는 `PRAGMA user_version` 이라는 정수 슬롯이 있어서
현재 스키마 버전을 DB 파일 자체에 기록해 둘 수 있다. 기동 시 이 값을 보고
필요한 변경만 적용하는 것이 **마이그레이션**의 가장 단순한 형태다.
M3 에서 본격적인 마이그레이션 도구를 쓰게 될 텐데, 그 개념을 여기서 최소 형태로 먼저 겪는다.

## 4. 장점 (이 기술이 잘하는 것)

- **`ON CONFLICT DO UPDATE` 한 문장이 M1 완료 조건 전체를 해결했다.**
  "두 번 실행해도 중복이 생기지 않는다"를 애플리케이션 코드로 풀면
  "먼저 조회하고 있으면 UPDATE, 없으면 INSERT" 같은 분기가 필요하고, 그 사이에 경쟁 상태가 생긴다.
  DB 에 맡기니 코드가 사라지고 정확해졌다. 실제로 재실행 시 336행을 매번 쓰지만
  총 행 수는 70125로 고정된다
- **제약이 실제로 버그를 막는다.** 외래키와 CHECK 제약을 테스트로 확인해 뒀는데,
  등록되지 않은 심볼의 가격을 넣으려 하면 그 자리에서 막힌다.
  "저장은 됐는데 나중에 보니 이상한 종목이 섞여 있다"가 원천적으로 불가능해진다
- **설정이 전혀 없다.** 서버 기동, 사용자 생성, 접속 정보 관리가 없다.
  `uv sync` 한 번으로 개발 환경이 완성된다는 M0 의 성질이 여기서도 유지됐다
- **트랜잭션 하나로 7만 행을 14초 만에 쓴다.** `executemany` 를 `with conn:` 안에서 한 번에 돌린다.
  행마다 커밋했다면 훨씬 느렸을 것이다
- **`PRAGMA user_version` 으로 마이그레이션을 20줄에 만들었다.** DB 파일이 자기 스키마 버전을
  들고 있으니 별도 관리 테이블이 필요 없다. 코드가 아는 버전보다 파일 쪽이 높으면 거부하게 해서,
  구버전 코드가 신버전 DB 를 건드리는 사고도 막았다

## 5. 한계점 / 트레이드오프

이 절이 M3 에서 PostgreSQL 로 옮기는 근거가 된다.

- **타입을 강제하지 않는다.** `INTEGER` 열에 문자열이 들어가도 받아준다.
  결국 `CHECK` 제약을 직접 붙여 막았는데, 다른 DB 라면 타입 선언만으로 되는 일이다.
  **DB 가 해 줄 일을 스키마 작성자가 기억해서 해야 한다**는 것이 이 방식의 비용이다
- **날짜 타입이 없다.** `TEXT` 에 ISO 8601 로 넣는 규약을 정하고, 코드 양쪽에서
  문자열↔`date` 변환을 직접 했다. PostgreSQL 의 `DATE` 타입이었다면 이 변환 코드가 없다
- **외래키 강제가 기본 꺼짐이다.** 커넥션마다 `PRAGMA foreign_keys = ON` 을 해 줘야 한다.
  이걸 모르면 외래키를 선언해 놓고 안 지켜지는 상태로 운영하게 된다.
  테스트로 켜져 있음을 확인해 둔 이유다
- **쓰기가 하나뿐이다.** 지금은 수집 배치 하나만 쓰므로 문제가 없다. 하지만 M4 에서
  API 서버가 뜨고 수집 배치가 동시에 도는 구조가 되면 이 제약이 드러난다.
  WAL 모드로 읽기·쓰기 동시성은 확보했지만, 쓰기끼리는 여전히 직렬이다
- **확장(extension)이 없다.** 이것이 결정적이다. M3 에서 임베딩 벡터를 저장하고
  근사 최근접 검색을 하려면 pgvector 가 필요한데, SQLite 에는 대응물이 마땅치 않다.
  **기능이 부족해서가 아니라 확장 생태계 때문에 옮기게 된다**
- **네트워크 계층을 배울 기회가 없다.** 접속 정보, 커넥션 풀, 인증, 격리 수준 같은 개념이
  등장하지 않는다. 이 프로젝트가 CS 지식 확장을 목표로 하는 이상 이건 단점 쪽에 가깝다

## 6. 왜 이 프로젝트에서 이 기술을 선택했는가

- **D-2(학습 우선, 단계적 업그레이드)의 정확한 사례다.** 5절의 한계는 지금 다 아는 것이지만,
  **읽어서 아는 것과 겪어서 아는 것은 다르다.** M3 에서 PostgreSQL 로 옮길 때
  "왜 옮기는가"에 대한 답이 추측이 아니라 경험이 되는 것이 이 선택의 목적이다
- **SQL 이 거의 같아서 이전 비용이 낮다.** SQLite 와 PostgreSQL 은 둘 다 행 지향 OLTP 이고
  `ON CONFLICT DO UPDATE` 문법까지 공유한다. DuckDB 를 골랐다면 분석 쿼리는 더 빨랐겠지만,
  OLAP 지향이라 M3~M4 에서 필요한 것(확장 생태계, 서빙)과 방향이 다르고 이전도 더 멀어진다
- **파일이냐 DB 냐**는 고민하지 않았다. 수정 종가가 소급 변경되므로 부분 수정이 필수이고,
  그 순간 Parquet 은 후보에서 빠진다
- **지금 규모에 정확히 맞는다.** 7만 행, 하루 한 번 쓰기, 단일 사용자.
  이 조건에서 PostgreSQL 을 띄우는 것은 순수한 운영 부담일 뿐이다
- **실서비스였다면?** 처음부터 PostgreSQL 로 갔을 것이다. 다중 쓰기와 확장 생태계는
  나중에 필요해질 게 확실하고, 실서비스에서는 이전 작업 자체가 리스크이기 때문이다.
  **개인 학습 프로젝트이기 때문에 성립하는 선택**이다
