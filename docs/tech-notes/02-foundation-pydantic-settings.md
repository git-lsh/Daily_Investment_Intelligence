# pydantic-settings (설정 관리) 정리

- 카테고리: Foundation
- 도입 시점: 2026-08-27
- 관련 코드 위치: `src/dii/config.py`, `.env.example`, `tests/test_config.py`

> 작성 상태: **회고완료**
> 이 노트는 uv 도입과 같은 M0 작업 단위에서 함께 진행해, 초안과 회고를 한 번에 작성했다.

## 1. 이 기술을 이해하기 위한 사전 지식

- **환경변수**: 프로세스가 OS 로부터 물려받는 key-value 문자열 쌍. 부모 프로세스에서 자식으로
  상속되며, **값이 항상 문자열**이라는 점이 중요하다. `DII_LOG_LEVEL=DEBUG` 를 넣으면
  파이썬에서는 `os.environ["DII_LOG_LEVEL"]` 이 `"DEBUG"` 라는 `str` 로 보인다
- **`.env` 파일**: 환경변수를 파일로 적어 두고 프로세스 시작 시 읽어 들이는 관행.
  OS 기능이 아니라 라이브러리가 흉내 내는 것이다. **커밋하지 않는 것이 대전제**다
- **12-factor app 의 config 원칙**: 환경마다 달라지는 값(DB 주소, API 키, 로그 레벨)은
  코드가 아니라 환경에 둔다. 같은 이미지·같은 코드가 환경변수만 바꿔 개발/운영 모두에서 돌아야 한다
- **직렬화와 역직렬화**: 문자열로 들어온 `"8080"` 을 `int` 로, `"true"` 를 `bool` 로 바꾸는 변환.
  설정 라이브러리가 하는 일의 상당 부분이 이것이다
- **Pydantic**: 타입 힌트를 런타임 검증 규칙으로 사용하는 데이터 검증 라이브러리.
  `pydantic-settings` 는 그 위에 "값을 환경변수에서 읽어 온다"를 얹은 것이다

## 2. 기술 개념 정리

`pydantic-settings` 의 `BaseSettings` 는 **필드 선언 = 설정 스키마**다. 클래스에 타입과 기본값을
적어 두면, 인스턴스를 만드는 순간 지정된 소스들에서 값을 찾아 채우고 타입을 변환한 뒤 검증한다.

값을 찾는 **우선순위**가 정해져 있다 (앞이 강함).

1. 코드에서 직접 넘긴 인자 — `Settings(log_level="DEBUG")`
2. 환경변수
3. `.env` 파일
4. 시크릿 파일 (`/run/secrets/...` 같은 컨테이너 시크릿 마운트)
5. 필드에 적은 기본값

이 순서 덕분에 **"기본값은 코드에, 로컬 개발값은 `.env` 에, 운영값은 환경변수에"** 라는 배치가
자연스럽게 성립한다. 컨테이너 배포(M5)에서 `.env` 없이 환경변수만 주입해도 그대로 동작한다.

핵심 동작을 말로 풀면,

- `env_prefix="DII_"` 를 주면 필드 `log_level` 은 환경변수 `DII_LOG_LEVEL` 을 찾는다.
  접두사는 다른 프로그램의 환경변수와 이름이 겹치는 사고를 막는다
- 타입 힌트가 곧 파서다. `data_dir: Path` 로 선언하면 문자열이 `Path` 로 변환되고,
  `app_env: AppEnv`(StrEnum) 로 선언하면 열거형에 없는 값은 거부된다
- `field_validator` 로 변환·검증 규칙을 추가할 수 있다. 이 프로젝트에서는 로그 레벨을
  대문자로 정규화하고, 표준 라이브러리가 아는 레벨이 아니면 실패시키는 데 썼다

**대안과의 비교**

| 방식 | 타입 변환 | 검증 | 오류 시점 | 비고 |
|---|---|---|---|---|
| `os.environ.get()` 직접 사용 | 수동 | 없음 | 값을 쓰는 순간 (런타임 깊숙이) | 의존성 0. 설정이 몇 개뿐이면 충분 |
| `python-dotenv` 단독 | 수동 | 없음 | 위와 같음 | `.env` 를 읽어 `os.environ` 에 넣어 줄 뿐 |
| `dataclass` + 수동 파싱 | 수동 | 수동 | 기동 시 (직접 짜면) | 결국 pydantic 이 하는 일을 손으로 다시 만들게 됨 |
| **pydantic-settings** | 자동 | 자동 | **기동 시** | 스키마가 곧 문서. 이미 pydantic 생태계라면 추가 비용 적음 |

## 3. AI/ML 엔지니어 관점에서 알아두면 좋은 개념

- **Fail fast (빠른 실패)**: 이 라이브러리의 진짜 가치는 편의가 아니라 **오류가 터지는 시점을
  앞당기는 것**이다. 오타 난 로그 레벨을 30분짜리 수집 배치가 다 끝난 뒤 리포트 단계에서
  발견하는 것과, 프로세스 시작 0.1초에 발견하는 것은 완전히 다른 문제다.
  ML 파이프라인에서 잘못된 하이퍼파라미터로 몇 시간 학습을 돌려 본 경험과 같은 종류의 문제다
- **설정을 경계에서 검증한다(validation at the boundary)**: 외부에서 들어온 신뢰할 수 없는
  문자열을 프로그램 가장 바깥에서 한 번 검증해 내부 타입으로 바꾸고, 안쪽 코드는 그 타입을
  믿고 쓴다. 이 발상은 M4 의 API 요청 검증, M1 의 수집 응답 파싱에도 그대로 적용된다
- **시크릿을 코드·이미지·저장소에서 분리하기**: API 키가 `.env` 에 있고 `.env` 가 `.gitignore` 에
  있어야, 저장소를 공개해도 사고가 나지 않는다. `.env.example` 을 대신 커밋해서
  "무엇을 채워야 하는지"만 공유하는 것이 표준 관행이다
- **설정 캐싱과 테스트의 충돌**: 설정을 프로세스 단위로 캐시(`lru_cache`)하면 편하지만,
  테스트에서 환경변수를 바꿔도 캐시된 값이 나온다. 이 프로젝트는 `get_settings.cache_clear()` 를
  테스트 픽스처에서 호출해 해결했다. **전역 상태를 두면 테스트 격리 비용이 따라온다**는
  일반 원칙의 구체적 사례다

## 4. 장점 (이 기술이 잘하는 것)

- **`Settings` 클래스 하나가 설정 문서 역할을 한다.** 어떤 설정이 있고 타입이 뭐고 기본값이
  뭔지가 한 화면에 있다. 별도 문서를 만들고 동기화할 필요가 없다
- **잘못된 값이 기동 시점에 잡힌다.** `DII_LOG_LEVEL=LOUD` 로 실행하면 즉시 실패하고,
  가능한 값 목록까지 메시지에 나온다. 이 동작은 테스트로 고정해 뒀다
- **접두사 규칙이 실수를 줄인다.** `DII_` 를 붙이는 것만으로 다른 도구의 환경변수와 섞이지 않는다
- **테스트가 쉽다.** `Settings(_env_file=None, log_level="WARNING")` 처럼 생성자 인자로
  덮어쓸 수 있어, 파일 시스템이나 환경을 건드리지 않고 설정 조합을 테스트할 수 있다

## 5. 한계점 / 트레이드오프

- **의존성이 하나 늘고, 그게 pydantic 이다.** pydantic 은 가벼운 라이브러리가 아니다
  (`pydantic-core` 는 컴파일된 확장이다). 설정이 필드 네 개뿐인 지금 시점만 보면 과하다.
  M4 에서 API 스키마로 pydantic 을 어차피 쓸 것을 전제로 한 선택이다
- **타입 체커와의 마찰**: `BaseSettings` 는 `_env_file` 같은 언더스코어 인자를 런타임에 처리하는데
  이게 시그니처에 드러나지 않아, 테스트에서 `# type: ignore[call-arg, arg-type]` 을 붙여야 했다.
  동적 동작과 정적 타입 검사가 부딪히는 전형적인 지점이다
- **`lru_cache` 로 감싼 것은 편의를 위한 타협이다.** 전역 접근점이 생기는 대신,
  테스트마다 캐시를 비워야 하는 규칙이 생겼다. 규모가 커지면 설정 객체를 인자로 넘기는
  의존성 주입 방식으로 바꾸는 편이 낫다 (실제로 `setup_logging(settings)` 는 그렇게 만들었다)
- **파일 기반 설정에는 맞지 않는다.** 유니버스 종목 리스트처럼 구조가 있고 길이가 긴 설정은
  환경변수에 담기 부적절하다. M1 에서는 이런 값을 별도 설정 파일로 두고,
  그 **파일 경로만** 환경변수로 받는 식으로 나눌 예정이다

## 6. 왜 이 프로젝트에서 이 기술을 선택했는가

- 이 프로젝트는 시작부터 **외부 API 키(M3 의 SEC 신원 표기, M4 의 LLM 키)** 를 다룰 것이 확정되어 있다.
  시크릿을 코드에서 분리하는 구조는 나중에 얹기보다 M0 에 깔아 두는 편이 싸다
- **D-3(로컬 → 클라우드)** 때문에 "같은 코드가 환경만 바꿔 돌아가야 한다"가 요구사항이다.
  `.env`(로컬)와 환경변수(컨테이너) 우선순위가 이미 정의되어 있는 라이브러리를 쓰는 것이
  이 요구사항에 정확히 대응한다
- **D-2(학습 우선, 단계적 업그레이드)와의 관계**: 설정 관리는 uv 와 마찬가지로 학습 대상이 아니라
  받침대다. `os.environ` 으로 시작했다가 갈아타 봐야 배우는 것은 "검증이 없으면 늦게 터진다"
  하나뿐이고, 그건 겪지 않아도 아는 것이다. 그래서 여기서는 단계적 업그레이드를 적용하지 않았다
- **실서비스였다면?** 기본 구조는 같았을 것이다. 다만 시크릿은 `.env` 가 아니라
  전용 시크릿 관리 서비스에서 주입받고, `pydantic-settings` 의 시크릿 파일 소스(우선순위 4번)를
  써서 컨테이너에 마운트하는 방식을 택했을 것이다
