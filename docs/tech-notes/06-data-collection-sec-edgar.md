# SEC EDGAR (공시 수집) 정리

- 카테고리: Data Collection
- 도입 시점: 2026-08-27
- 관련 코드 위치: `src/dii/collect/filings.py`, `src/dii/collect/news.py`

> 작성 상태: **회고완료**
>
> 뉴스 수집(yfinance 내장)도 이 노트에서 함께 다룬다. 별도 라이브러리를 쓰지 않고
> 이미 있는 의존성을 쓰는 것이라 한 편으로 충분하다.

## 1. 이 기술을 이해하기 위한 사전 지식

### 미국 공시 제도

- **EDGAR**: 미국 증권거래위원회(SEC)가 운영하는 전자공시 시스템. 상장사는 법적으로
  여기에 서류를 제출해야 하고, **전부 공개된다.** 유료 데이터 벤더를 거치지 않고
  원문에 직접 접근할 수 있다는 것이 이 소스의 근본적 장점이다
- **CIK (Central Index Key)**: SEC 가 각 제출자에게 부여하는 10자리 식별자.
  **티커가 아니라 CIK 가 진짜 식별자다.** 티커는 바뀌지만 CIK 는 바뀌지 않는다
- 주요 서식(form type):
  - **8-K** — 수시공시. 인수합병, 경영진 교체, 실적 발표 등 "무슨 일이 생겼을 때" 낸다.
    이 프로젝트가 가장 관심 있는 종류다
  - **10-Q** — 분기 보고서. **10-K** — 연간 보고서
  - **Form 4** — 내부자 거래 신고. 건수가 압도적으로 많다(AAPL 최근 1001건 중 588건).
    개별 임원의 소량 매매까지 전부 잡혀 신호 대 잡음비가 낮다
- **accession number**: 제출 건마다 붙는 고유 번호. 이걸 중복 제거 키로 쓴다

### 웹 API 예절

- **User-Agent 로 신원을 밝혀야 한다.** SEC 는 요청 헤더에 **연락 가능한 이메일**을 요구한다.
  없으면 차단된다. 이건 기술적 제약이 아니라 **약속**이다 — 문제가 생겼을 때 연락할 곳을
  남기라는 뜻이다
- **초당 10회 제한.** 넘으면 차단된다. 뚫는 것이 아니라 맞춰 주는 것이 목적이다
- **gzip 압축 수용**: `Accept-Encoding: gzip` 을 보내면 전송량이 줄어든다.
  상대 서버의 대역폭을 아끼는 것이기도 하다

## 2. 기술 개념 정리

### 쓰는 엔드포인트 세 가지

| 용도 | 엔드포인트 | 성격 |
|---|---|---|
| 티커 → CIK 매핑 | `www.sec.gov/files/company_tickers.json` | 정적 파일. 10,388개. 하루 한 번이면 충분 |
| 제출 이력 | `data.sec.gov/submissions/CIK{10자리}.json` | 회사별 최근 1,000여 건 |
| 전문 검색 | `efts.sec.gov/LATEST/search-index?q=...` | 본문 검색. 이번 단계에서는 쓰지 않는다 |

제출 이력 응답은 **열 지향(columnar)** 이다. `filings.recent` 아래에
`form`, `filingDate`, `accessionNumber` … 가 **각각 같은 길이의 배열**로 들어 있고,
같은 인덱스끼리 짝을 이룬다. 레코드 배열이 아니라 배열의 묶음이라는 점을 놓치면 파싱이 틀어진다.

### 뉴스는 yfinance 내장 기능을 쓴다

`Ticker.news` 가 종목당 10건 내외의 최근 기사를 돌려준다. 제목, 요약, 발행 시각,
발행처, 원문 URL 이 들어 있다. **키 발급이 없고 이미 의존성에 있다.**

무료 대안과 비교했을 때의 위치:

| 소스 | API 키 | 과거 이력 | 이 프로젝트 관점 |
|---|---|---|---|
| **yfinance 내장** | 불필요 | 최근 것만 | 매일 돌리면 이력이 쌓인다. 시작점으로 충분 |
| RSS 피드 | 불필요 | 최근 것만 | 소스마다 형식이 달라 파서를 여럿 만들어야 한다 |
| Finnhub 무료 티어 | 필요 | 1년 | 키 관리가 생기지만 이력이 있다. 다음 후보 |
| NewsAPI 무료 티어 | 필요 | 1개월, 하루 100요청 | 44종목 일일 수집에 요청 한도가 빠듯하다 |

**최근 것만 준다는 한계는 매일 수집해 쌓는 것으로 메운다.** 오늘 시작하면 오늘부터 이력이 생긴다.
과거를 소급해 채울 수 없다는 것은 받아들이고 시작한다.

### 저장 모델 — 다대다 관계

기사 하나가 여러 종목을 언급할 수 있고, 종목 하나에 기사가 여럿 붙는다. **다대다**다.

```
document          document_symbol         security
(기사/공시 1건)  ← (연결) →              (종목)
```

`document` 에 기사 내용을 한 번만 저장하고, `document_symbol` 이라는 **연결 테이블**로
어떤 종목과 엮이는지를 표현한다. 기사 본문을 종목 수만큼 복사해 넣는 것보다
저장 공간과 일관성 양쪽에서 낫다 — 이것이 정규화가 하는 일이다.

## 3. AI/ML 엔지니어 관점에서 알아두면 좋은 개념

### 신호 대 잡음비를 수집 단계에서 관리한다

AAPL 의 최근 제출 1,001건 중 588건이 Form 4(내부자 거래)다. 전부 저장하면 데이터베이스의
절반 이상이 "임원 아무개가 주식 500주를 팔았다"로 채워진다. **그러면 M3 의 검색과
M4 의 Agent 가 그 잡음을 뚫고 의미 있는 공시를 찾아야 한다.**

수집 단계에서 서식 종류로 거르는 것이 훨씬 싸다. ML 에서 "데이터 정제를 앞단에서 할수록
뒷단이 쉬워진다"는 것과 같은 이야기인데, 여기서는 그 앞단이 수집기다.

### 예의를 코드로 표현한다

rate limit 을 지키는 코드는 기능이 아니라 **태도**다. 남의 무료 서비스를 쓰면서
초당 100번 때리면 차단당하는 것이 당연하고, 차단당해도 할 말이 없다.

- 요청 사이에 최소 간격을 둔다 (SEC 는 초당 10회 → 최소 0.1초 간격)
- User-Agent 에 연락처를 남긴다
- 실패했을 때 즉시 재시도하지 않고 간격을 늘려 가며 재시도한다 (지수 백오프)

**이 프로젝트에서 이 값들을 설정으로 빼는 이유**는, 나중에 SEC 가 정책을 바꿨을 때
코드를 고치지 않고 대응하기 위해서다.

### 시각 처리 — 날짜와 타임스탬프가 섞인다

SEC 공시는 **날짜**(`2026-07-31`)만 준다. 뉴스는 **타임스탬프**(`2026-08-27T03:52:08Z`)를 준다.
둘을 한 테이블에 넣으려면 규약이 필요하다.

이 프로젝트는 **UTC ISO 8601 문자열**로 통일하고, 날짜만 있는 것은 그날 자정(UTC)으로 본다.
정밀도를 잃지만, 비교와 정렬이 문자열 사전순으로 동작한다는 이점이 그보다 크다.
타임존을 섞어 저장하면 "어제 뉴스"가 조회 위치에 따라 달라지는 버그가 생긴다.

### 외부 식별자로 멱등성을 만든다

M1 에서는 `(종목, 날짜)` 가 자연 키였다. 여기서는 그런 것이 없다 —
같은 날 같은 종목에 기사가 여러 건 나온다.

대신 소스가 주는 **외부 식별자**를 쓴다. SEC 는 accession number, 뉴스는 기사 id 다.
`(source, external_id)` 에 유일 제약을 걸면 M1 과 똑같이 UPSERT 로 멱등성이 성립한다.

**외부 식별자를 신뢰할 수 있는가**는 따져 볼 문제다. SEC 의 accession number 는
제도적으로 보장되지만, 뉴스 id 는 그 소스의 내부 값이라 언제든 바뀔 수 있다.
바뀌면 같은 기사가 두 번 들어오는데, 치명적이지 않으므로 감수한다.

## 4. 장점 (이 기술이 잘하는 것)

- **뉴스가 키 발급 없이 즉시 동작했다.** 56종목 560건을 30초에 받았다.
  이미 있는 의존성이라 설치도, 계정 생성도, 키 관리도 없었다.
  M3 를 시작하는 마찰이 사실상 0 이었던 것이 실질적인 이득이다
- **다대다 설계가 바로 값을 했다.** 560건을 처리했는데 저장된 문서는 481건이었다.
  차이 79건은 여러 종목에 동시에 걸린 기사다. 한 ETF 시황 기사는 8개 종목
  (SPY, XLE, XLF, XLI, XLK, XLP, XLV, XLY) 에 엮였다.
  **종목마다 본문을 복사했다면 같은 기사를 8번 저장했을 것이고**, 나중에 그 8벌이
  전부 임베딩 대상이 되어 검색 결과를 같은 기사로 도배했을 것이다
- **`(source, external_id)` 유일 제약이 M1 의 `(종목, 날짜)` 와 똑같은 역할을 했다.**
  자연 키가 없는 데이터에서도 소스가 주는 식별자만 있으면 멱등성이 그대로 성립한다
- **SEC 응답이 놀랍도록 잘 정리되어 있다.** 공식 API 답게 CIK 매핑(1만여 건)과
  제출 이력이 단순한 JSON 하나로 온다. 인증도, 키도, 페이지네이션도 없다.
  비공식 API 인 yfinance 와 대비된다
- **Form 4 를 거른 효과가 숫자로 나왔다.** 44종목 180일치를 받아 411건이 남았고,
  그중 8-K 가 316건이다. 거르지 않았다면 수천 건이 들어왔을 것이고 대부분이
  임원 개인의 소량 매매였을 것이다
- **초당 10회 제한을 지키면서도 44종목이 12초에 끝났다.** 제한을 지키는 것과 느린 것은
  다른 문제라는 걸 확인했다. 요청 수 자체가 적으면(종목당 1회) 간격 제약이 병목이 아니다

## 5. 한계점 / 트레이드오프

- **뉴스에 과거 이력이 없다.** 종목당 최근 10건뿐이다. 오늘 시작하면 오늘부터 쌓인다.
  M2 처럼 "과거 임의 시점"을 재현하려 해도 그 시점의 뉴스는 없다.
  **파이프라인은 as-of 를 지원하지만 데이터가 못 따라가는 상태**이고, 이건 매일 돌려 메우는 수밖에 없다
- **뉴스 id 를 신뢰할 근거가 약하다.** SEC 의 accession number 는 제도적으로 보장되지만,
  yfinance 의 기사 id 는 내부 값이라 언제든 바뀔 수 있다. 바뀌면 같은 기사가 두 번 들어온다.
  치명적이지 않아 감수하지만, "외부 식별자면 다 같은 것이 아니다"를 알고 쓴다
- **종목 연결이 소스가 준 그대로다.** "이 기사는 AAPL 을 조회했을 때 나왔다"는 것 이상의
  근거가 없다. ETF 시황 기사가 8종목에 걸린 것도 실제로 그 8종목을 다뤄서가 아니라
  각 종목 조회에 등장했기 때문이다. **본문에서 종목을 추출하는 것과는 다르다**
- **SEC 는 신원 표기 없이는 아예 못 쓴다.** 연락 가능한 이메일이 필요하고, 이건 코드로
  해결할 수 없다. 배포(M5)에서 시크릿으로 주입해야 할 항목이 하나 늘었다
- **ETF 는 SEC 에 CIK 가 없다.** 처음에 유니버스 56심볼 전체를 SEC 에 물었더니
  SPY 와 섹터 ETF 11개가 "CIK 없음"으로 실패했다. **버그가 아니라 제도의 성질**이다 —
  ETF 는 신탁 구조라 개별 기업처럼 8-K/10-Q 를 제출하지 않는다.
  그대로 뒀다면 매일 12건이 실패로 보고돼, M5 의 "실패하면 알림"이 매일 울렸을 것이다.
  **정상인 것을 실패로 분류하면 알람이 무의미해진다** — SEC 대상을 개별 종목 44개로 좁혀 해결했다.
  뉴스는 반대로 ETF 에도 시황 기사가 붙으므로 전체를 대상으로 둔다
- **rate limit 구현이 단순하다.** 요청 사이 간격만 강제하는 방식이라 동시 요청을 도입하면
  바로 무너진다. 지금은 순차 수집만 하므로 충분하지만, 한계를 알고 쓴다
- **`requests` 대신 표준 라이브러리 `urllib` 을 썼다.** 의존성을 늘리지 않으려는 선택인데,
  대신 gzip 해제와 재시도를 직접 짜야 했다. 소스가 늘어나면 `requests` 나 `httpx` 로
  옮기는 편이 낫다

## 6. 왜 이 프로젝트에서 이 기술을 선택했는가

- **무료·키 불필요가 조건이었다.** SEC 는 공공 데이터라 그 자체로 만족하고,
  뉴스는 후보 중 유일하게 키 없이 되는 것이 yfinance 내장 기능이었다.
  Finnhub 나 NewsAPI 는 이력이 있어 매력적이지만 키 관리가 생긴다 —
  **M3 의 학습 목표는 뉴스 소스가 아니라 검색이므로**, 여기에 복잡도를 쓰지 않는 편이 맞다
- **Form 4 를 거른 것**이 가장 실질적인 판단이었다. AAPL 최근 제출 1,001건 중 588건이 Form 4 다.
  전부 저장하면 DB 절반이 임원의 소량 매매로 채워지고, 그 잡음을 M3 검색과 M4 Agent 가
  뚫어야 한다. **정제를 앞단에서 할수록 뒷단이 쉬워진다**는 원칙 그대로다
- **원문 본문을 저장하지 않는 것**도 의도적이다. 저작권 문제를 피하고, 검색에는 제목·요약으로
  충분하다. 원문이 필요하면 URL 로 간다
- **실서비스였다면?** 뉴스는 유료 API 로 갔을 것이다. 과거 이력 없이는 백테스트도,
  "작년 이맘때 무슨 일이 있었나"도 답할 수 없다. 종목 연결도 소스가 준 것에 의존하지 않고
  본문에서 개체명을 추출해 검증했을 것이다
